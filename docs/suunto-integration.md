# Suunto 24/7 Health Integration

This document is the source of truth for the Suunto 24/7 Health ingestion added by issue #612. It supplements the repository-wide [provider integration guide](provider-integration-guide.md), [unified Health model](unified-health-data.md), and [Sleep sync operations](sleep-sync-operations.md).

Suunto 24/7 Health is available production-wide for active connected Suunto accounts. `functions/src/suunto/health-flags.ts` remains the source-controlled kill switch, independent from Suunto Sleep enablement. An authenticated App Check-protected callable returns the current Health availability so the History Import UI follows that switch without treating retained Health sync state as authorization.

## Provider contract

Suunto exposes three relevant pull resources. Every request is authenticated with the connected user's OAuth access token and the Suunto subscription key. Suunto documents the stable account identity in the access token JWT's custom `user` claim; OAuth exchange and refresh handling normalize that claim before credential persistence. A legacy top-level `user` response field is accepted only when it agrees with the claim, and any mismatch with the expected retained account is rejected.

| Resource | Request/range behavior | Used fields |
| --- | --- | --- |
| `/247samples/activity` | Internal half-open millisecond range translated to Suunto's inclusive `to=end-1`, at most 28 days | `HR`, `HRExt.Min`, `HRExt.Max`, `HRV`, `SpO2`, `Altitude`, `StepCount`, `EnergyConsumption` |
| `/247samples/daily-activity-statistics` | ISO start/end range, at most 28 days | `stepcount` and `energyconsumption`, grouped by aggregation and device source |
| `/247samples/recovery` | Internal half-open millisecond range translated to Suunto's inclusive `to=end-1`, at most 28 days | `Balance`, `StressState` |

The corresponding documented webhook notifications are `SUUNTO_247_ACTIVITY_CREATED` and `SUUNTO_247_RECOVERY_CREATED`. They are handled by the existing signed Suunto webhook endpoint. The notification payload is used only to identify bounded local-day refetch windows; raw Health samples from the webhook are never placed in Firestore, the queue, or Health collections. After signature and bounded-shape validation, the handler resolves every active Firebase connection through the indexed server-only `suuntoHealthWebhookAccountBindings` collection. Each binding is keyed by a one-way digest of the provider account and Firebase UID together. Those browser-inaccessible reverse bindings are written atomically with new Suunto OAuth credentials. For an active legacy credential, `scheduleSuuntoWebhookBindingVerification` may create a missing binding only after a forced provider token refresh returns the same exact provider account identity as both the server-read token document ID and its canonical `userName`; a locally stored token record alone is never webhook authority. The migration scheduler runs every 30 minutes and keyset-pages only the server-owned `suuntoAppAccessTokens` roots, never a cross-provider `tokens` collection group. Root and retained-token pages are independently bounded, and a nested token cursor ensures accounts beyond the first child page are processed on later invocations. The short-lived raw child key exists only in the backend-only maintenance cursor and is cleared when that root completes; it is never logged or copied into Health data. Failed credentials receive their own exponential-backoff fields on the already server-owned token document, while the main cursor advances so one permanently invalid credential cannot block later users. Production-wide Sleep polling uses an independent nested canonical-root/token keyset cursor, advances one bounded page every 30 minutes until a sweep finishes, then pauses that cursor for 24 hours. Sweep age is logged before it approaches the seven-day reconciliation window; insertions or deletions before the cursor cannot shift already visited roots, and Suunto-shaped rows under a different provider tree cannot consume a page. The ingress transaction rechecks each exact binding and account credential, the current token-root lifecycle revision, authoritative connection metadata, and account deletion before creating one compact `suuntoHealthWebhookIngress` document per active connection. It then acknowledges Suunto and retryable Firestore triggers perform Cloud Tasks fan-out asynchronously. Signed payloads that are malformed, oversized, unknown, disconnected, or deleting are deliberate permanent drops and receive `2xx` without ingress persistence; authentication failures remain rejected, and transient identity/transaction failures return `5xx` so Suunto retries.

`SUUNTO_247_SLEEP_CREATED` uses the same server-owned bindings for production-wide Sleep delivery. Each binding also stores a one-way provider-account digest so the handler can perform one bounded indexed lookup without trusting locally stored token documents as identity authority. The handler revalidates every candidate binding against its exact user token, token root, connection metadata, rollout, and deletion state, then creates one user-namespaced `suunto_webhook` queue item per active Firebase connection. Queue admission transactionally rechecks the exact binding, account-token generation, token-root lifecycle, and connection fields and stores only an opaque digest of that authority. Before mapping the embedded Sleep payload, the worker captures the current full authority and requires the digest to match; every Sleep-session and sync-state write transaction then rechecks those fields. Previously queued work therefore cannot cross a disconnect, reconnect, OAuth replacement, binding replacement, or account deletion, while same-generation access-token rotation remains valid. Connecting one Suunto account to multiple Firebase users delivers the same signed Sleep notification independently to every active owner; one deleted or disconnected owner is skipped without suppressing the others, while a transient lookup or queue failure remains retryable. Fan-out is capped at 32 active bindings and fails retryably instead of silently omitting an owner when that bound is exceeded.

`WORKOUT_CREATED` and `ROUTE_UPDATED` also resolve the complete active binding set. They create independent Firebase-UID-namespaced workout and route queue items, and each worker remains bound to that UID's exact credential. A duplicate, deletion, disconnect, or terminal skip for one owner therefore cannot suppress another owner. Signed malformed or unknown-account notifications are acknowledged as permanent drops; transient binding or queue failures remain retryable. The same 32-binding cap applies.

Production setup must subscribe `SUUNTO_247_ACTIVITY_CREATED`, `SUUNTO_247_RECOVERY_CREATED`, and `SUUNTO_247_SLEEP_CREATED` to the canonical `receiveSuunto247Data` endpoint. Workout and Route notifications remain pointed at `insertSuuntoAppActivityToQueue` and `insertSuuntoAppRouteToQueue` respectively, all using the configured `SUUNTOAPP_NOTIFICATION_SECRET`. The retired `receiveSuuntoAppSleepData` endpoint must not be registered with Suunto. This repository change does not register provider webhooks or deploy Functions.

## Normalization

Suunto Health data is kept separate from workout FIT metrics and normalized Sleep sessions. The provider and source-record type remain explicit on every record.

| Suunto value | Unified Health representation | Decision |
| --- | --- | --- |
| `HR` | `heart_rate`, interval average | bpm |
| `HRExt.Min` / `HRExt.Max` | `heart_rate`, interval minimum/maximum | bpm |
| `HRV` | `heart_rate_variability`, interval sample | milliseconds |
| `SpO2` | `blood_oxygen_saturation` | Provider ratio multiplied by 100 to canonical percent |
| `Altitude` | `altitude` | meters |
| activity `StepCount` | `steps`, accumulated interval series | count; distinct from the daily statistic |
| activity `EnergyConsumption` | `total_energy`, accumulated interval series | joules divided by 4,184 to canonical kilocalories |
| daily `stepcount` | `steps`, provider daily total/average | canonical count |
| daily `energyconsumption` | `total_energy`, provider daily total/average | joules divided by 4,184 to canonical kilocalories |
| recovery `Balance` | `body_energy` | Provider ratio multiplied by 100 to canonical percent |
| recovery `StressState` | `stress_state` category | `1 relaxing`, `2 active`, `3 passive`, `4 stressful`; invalid sentinel `0` is omitted |

Missing values remain missing. Suunto can return complementary or corrected Activity/Recovery rows at one timestamp. Those rows merge per metric in provider response order: a later non-null value wins, while a later missing value or the Recovery `StressState` sentinel `0` cannot erase an earlier available measurement. Daily statistic nulls are ignored when a non-null value exists, while conflicting non-null values fail validation. Activity and recovery records are grouped by provider-local calendar date and UTC offset. A daylight-saving offset change therefore creates separate source records rather than pretending the whole local date used one offset.

Historical coverage is `unknown` because the provider does not assert completeness. The current provider-local date is `partial`. Activity and recovery observation freshness follows the latest accepted sample; daily statistics use the end of their bounded day. The expected refresh interval is 48 hours.

Daily statistics retain multiple devices as separate source records using a one-way device key derived from the provider account and Suunto source name. Activity and recovery feeds do not expose a device source in the documented sample shape, so those records deliberately have no device attribution.

## Ingestion and revision flow

```text
signed webhook ─> active UID bindings ─> durable ingress per UID ─> retryable fan-out ─┐
daily scheduler ────────────────────────────────────────────────┼─> sleepSyncQueue / suunto_health_poll
history import ─────────────────────────────────────────────────┘          │
                                                                            ▼
                                                                 lifecycle-fenced Suunto pulls
                                                                            │
                                                                            ▼
                                                                bounded mapper + Health writer
                                                                            │
                                                                            ├─ users/{uid}/healthSourceRecords
                                                                            ├─ users/{uid}/healthSampleChunks
                                                                            └─ users/{uid}/healthSyncState/SuuntoApp

signed Sleep webhook ─> indexed active UID bindings ─> one user-namespaced suunto_webhook queue item per UID
signed Workout webhook ─> indexed active UID bindings ─> one UID-namespaced workout queue item per UID
signed Route webhook ───> indexed active UID bindings ─> one UID-namespaced route queue item per UID
```

`scheduleSuuntoHealthSync` runs every 30 minutes so bounded 25-root account pages and retained-token pages can advance promptly, then its keyset cursor pauses for 24 hours after completing a production-wide sweep. The cursor's `global-v1` scope marker makes the first production-wide invocation ignore and overwrite the former staged position instead of inheriting its completed-sweep pause or abandoning its raw backend cursor fields. Each sweep refetches the rolling recent seven-day window for active connected accounts. Signed Activity/Recovery notifications durably stage immediate local-day reconciliation before acknowledgement; the ingress trigger then enqueues the work. The existing Suunto history callable keeps its deployed name and cooldown; while the Health kill switch is enabled, each 28-day Sleep range also queues a matching Health range for every connected Suunto account and the UI calls it **Import Sleep & Health History**. One request accepts at most eight connected Suunto accounts so a retained-account set cannot create an unbounded queue fan-out. The existing Sleep backfill continues to use its established first-usable-account behavior.

The short-lived, server-only schema-v5 ingress contains one already-bound Firebase UID, notification type, provider account ID needed to revalidate the credential, the account token generation, the current token-root OAuth revision, captured connection generations, bounded windows, receive time, processing status, and a seven-day TTL. Each schema-v3 reverse binding stores one UID, a one-way provider-account digest used for bounded shared-account lookup, its account token generation, and a server-set authorization source (`oauth_callback` or `provider_refresh`) behind a document key made from a separate one-way digest of the provider account and UID together; clients cannot read or write it. A schema-v3 row without recognized authorization provenance is rejected rather than grandfathered. Connecting the same Suunto account to another Firebase user adds an independent binding instead of transferring webhook ownership, and Suunto is exempt from the cross-user duplicate cleanup used by single-owner providers. The binding must match its exact token generation, but a retained Suunto account token is not required to equal the root's newest OAuth revision. Instead, webhook admission captures that current root revision as a separate durable lifecycle fence. The create transaction rechecks every candidate binding, exact token/root, service metadata, user root, and deletion tombstone. Unknown, disconnected, and deleting accounts therefore create no ingress row. Each ingress document ID is a one-way digest of the authenticated notification digest plus its bound UID, so exact retries collapse independently for every eligible connection; the raw notification and samples are not retained. The fan-out trigger also binds every completion or discard to the original Firestore create/update version. A delayed trigger from before disconnect cannot update or delete a same-ID ingress recreated by a later connection, while an ordinary retry of the same document remains idempotent. These documents are permanent leaves, so version-guarded document deletion is used instead of unguarded recursive deletion. Queue creation is transactionally fenced to the same per-user binding, token, root, and service-meta values, and the queue worker rejects a changed binding, token, root OAuth revision, or connection generation before provider I/O or embedded Sleep-payload mapping. Later same-day Activity or Recovery notifications receive a fresh refetch identity. Repeated poll/webhook/backfill work still resolves to deterministic Health source identities. Identical higher-order responses advance only the source record's maximum-observed revision watermark without rewriting sample chunks, and delayed distinct responses below that watermark remain stale. Provider source keys, account IDs, device source names, and revision tokens are hashed before Health persistence.

Each provider response is capped at 4 MiB and 10,000 activity or recovery samples. Activity, Recovery, and daily statistics are each capped at 256 mapped source records per queue item; daily statistics are additionally capped at 16 groups, 64 sources per group, and 64 samples per source. A pull includes one day of context on each side of its target and splits larger targets into 26-day segments, so no provider request exceeds 28 days and a range boundary cannot replace a previously complete local-day record with partial samples. Suunto's daily-statistics resource can include the current provider-local day beyond an older requested end date. The worker still validates every returned row against the response and shape bounds, then ignores any complete daily record that does not intersect the original target. Only full daily records intersecting that target are retained. Requests time out after 30 seconds. A provider 401 forces one guarded token refresh and one retry; all provider response, URL, token, and datastore detail is replaced with an opaque error before logs, queue retry fields, or sync state are written.

## Lifecycle and deletion

Every request and write is fenced to the original account token document credential, the token root's captured OAuth lifecycle revision, connection state, and connection generation. Firestore Rules deny browser creation, mutation, or deletion of both the Suunto token root and every token child; owner reads remain temporarily available for the existing connection UI, but they confer no webhook authority. Suunto can retain multiple account tokens, so an account token is not required to own the root's latest OAuth generation; all retained accounts remain usable while the captured root revision stays unchanged. A completed OAuth connection rotates that root revision and invalidates in-flight work across the account set without silently excluding older connected accounts. The provider-verification sweep transactionally upgrades active legacy connections that predate these generations: it mints only missing root, account-token, and connection generations, creates missing connected metadata, and advances the existing binding to the new account-token generation in the same transaction. That upgrade requires either the current server-owned provider-authorized binding or a fresh forced refresh whose provider identity matches the exact account; local legacy token data alone cannot authorize it. Existing nonempty generations are preserved, retained account generations remain independent from the newest root revision, malformed state fails closed, and deletion or disconnect prevents every migration write. Same-generation access/refresh-token rotation is not an authority change: if a guarded write observes only that rotation, the worker atomically recaptures the live credential, verifies that binding, account generation, root revision, connection generation, and deletion state are continuous, and retries the write a bounded number of times. Repeated rotation stays retryable instead of permanently acknowledging the queue row; reconnect, disconnect, binding removal, or deletion still fails closed. The worker checks account deletion before token resolution, before every provider request, and through the shared Health writer transaction. The binding-verification scheduler also rechecks the deletion tombstone and user root inside the transaction that records provider-derived verification or backoff state, so cleanup cannot race a post-refresh metadata write. A stale worker cannot adopt a later OAuth connection.

Connected and reconnect-required Suunto transitions mirror `ready` or `reconnect_required` into Health sync state for every connected user using a durable generation-keyed repair marker. Token-root deletion supersedes a pending projection while proving the root is absent, then projects `disconnected` unless current service metadata authoritatively owns reconnect-required. The scheduled lifecycle repair scans both COROS and Suunto markers.

Ordinary Suunto disconnect retains imported Workout, Route, Sleep, and Health history but stops new work. Guarded token cleanup removes only that Firebase user's matching reverse binding and recursively removes pending webhook ingress and UID-owned queue rows, including live `routeSyncQueue` work and its `failed_jobs` copies; other active users connected to the same Suunto account remain bound. The route-import worker revalidates the exact source connection before reading an unchanged saved route, before uploading a new original, inside the route-persistence transaction after provider I/O, and again immediately before enqueueing downstream route delivery. Before any GPX upload, the worker transactionally creates a backend-only reservation in top-level `routeOriginalFileCleanup`, after rechecking the account-deletion guard and exact source fence. The reservation records the one random object path and remains leased beyond the 540-second worker lifetime. If reservation persistence fails, no upload occurs. A rejected Storage upload is treated as ambiguous: the worker may attempt immediate deletion, but it neither releases nor accelerates the reservation because the object can become visible afterward. A known post-upload, pre-commit rejection makes three bounded Storage deletion attempts and accelerates that same reservation. If the transaction callback completed but its commit response is ambiguous, the worker preserves both file and reservation so delayed reconciliation can prove whether the route committed before touching Storage. A retry-enabled update trigger plus `redriveRejectedRouteOriginalCleanup` every 30 minutes prove the object is not referenced by the committed route, delete it, and only then delete the permanent-leaf reservation. Failed rows move behind a 30-minute retry time, so a persistent oldest failure cannot monopolize the bounded scan. A crash or failed acceleration cannot lose the path, and a failed post-commit reservation release preserves the committed original while discarding only the stale reservation. Account cleanup invokes the same reconciler from outside `users/{uid}` without deleting an active lease, so it neither recreates user descendants nor races an in-flight upload; the scheduled scan finishes any leased row after expiry. Malformed tasks are discarded without touching Storage. The persistence check uses the originally captured fence, so a disconnect or reconnect that wins during export/parsing prevents route, provenance, processing, and quota writes while any previously stored original remains intact. It carries the UID connection generation, exact account-token generation, and root OAuth revision into the downstream queue; queue admission rechecks them in its write transaction, and the delivery worker rechecks them when claiming and immediately before provider delivery. Work that races cleanup or reconnect therefore fails closed against the lifecycle that authorized it. Account deletion additionally queries and recursively deletes any reverse binding still owned by the UID, then removes the Suunto token subtree, every matching workout, route, `suuntoHealthWebhookIngress`, `sleepSyncQueue`, and DLQ row (including `suunto_health_poll`), and recursively removes imported user data under `users/{uid}`. Binding removal is ownership-guarded and also generation-guarded where cleanup can race credential replacement, so delayed cleanup cannot delete a newer credential binding for the same user. The ingress trigger rechecks the live kill switch, exact token binding, connection state, and account-deletion guard before fan-out. Malformed, disabled, unbound, deleting, or lifecycle-skipped ingress is deleted only if its original Firestore version is still current; only successful fan-out retains a processed row until TTL. Successful completion is likewise version-guarded, so concurrent cleanup or reconnect cannot recreate, complete, or delete a replacement ingress document. TTL is only a fallback for successfully processed or transiently stranded operational rows. Deletion-aware completion, retry, and DLQ transitions cannot recreate removed work.

## Operations and rollback

The existing Sleep queue/Cloud Task worker carries both Sleep and Health work. Admin Queue Monitor labels it **Sleep & Health Sync** and exposes the existing pending, retry, lag, provider, and DLQ views. Health queue documents remain distinguishable by `type: suunto_health_poll` and `healthTrigger: poll | webhook | backfill`. Operations must also monitor failures and aging unprocessed documents for `fanOutSuuntoHealthWebhookIngress`; Eventarc retries transient fan-out or version-guarded delete failures, while successfully processed ingress remains short-lived until TTL cleanup.

Before enabling production-wide Health:

1. Confirm the Suunto production entitlement covers all three pull resources and both webhook notification types.
2. Keep `SUUNTO_HEALTH_SYNC_ENABLED` true. There is no Suunto Health UID allowlist.
3. Deploy Firestore Rules first so the complete Suunto OAuth root and token subtree are browser-write denied and the binding and maintenance-state collections remain backend-only. Next deploy only the Suunto OAuth binding writer/cleanup and `scheduleSuuntoWebhookBindingVerification`; keep the currently deployed webhook consumers and queue worker unchanged during seeding. Verify the migration scheduler is active and has its Suunto OAuth secrets.
4. Invoke `scheduleSuuntoWebhookBindingVerification` enough times to complete a canonical-root and retained-token keyset sweep across all active legacy candidates before deploying webhook producers or the strict route lifecycle worker. The same provider-verified transaction backfills missing legacy root, account-token, and connection generations and updates the binding fence, so existing valid connections do not need to reauthorize. Use the structured selected/status-count logs plus `lastCompletedUserID`, `currentUserID`, `lastProcessedTokenID`, `sweepStartedAtMs`, and `lastCompletedSweepAtMs` in the backend-only maintenance cursor to confirm coverage. Investigate `unverified`, `inactive`, `failed`, and per-token backoff state; reconnect only credentials that cannot complete the forced refresh or whose returned identity does not match the stored account. Migration runs every 30 minutes independently from polling, advances past failed credentials, and retries each one on later sweeps after its own bounded backoff. Provider-pull queue work can perform the same exact provider verification on demand when its binding is still missing, but embedded Sleep webhook payloads always fail closed until a pre-existing authorized binding is present. Provenance-less bindings remain ineligible and may be overwritten only after provider verification; remove any such legacy rows and their queued webhook work before enabling webhook producers.
5. Only after binding seeding, deploy `scheduleSuuntoSleepSync`, `scheduleSuuntoHealthSync`, the shared dispatcher/worker, `cleanupRejectedRouteOriginalFile`, `redriveRejectedRouteOriginalCleanup`, `fanOutSuuntoHealthWebhookIngress`, `receiveSuunto247Data`, `insertSuuntoAppActivityToQueue`, and `insertSuuntoAppRouteToQueue`; then point Activity, Recovery, and Sleep 24/7 webhook notifications at `receiveSuunto247Data`. Deploy both rejected-original cleanup consumers and the top-level Firestore deny rule before the strict route worker so every pre-upload reservation has both immediate and indefinite recovery. This ordering prevents permanent `2xx` drops for Workout, Route, Sleep, or Health while bindings are absent and prevents the Health handler from accepting ingress before an asynchronous consumer exists.
6. Verify poll, webhook, history, 401 refresh, reconnect, disconnect, and account deletion. The first global poll resets the existing Health cursor through its `global-v1` scope marker and advances at most 25 canonical roots per 30-minute invocation before applying the normal 24-hour completed-sweep pause.
7. Monitor queue age/retries, malformed per-user bindings, opaque error categories, Health sync timestamps, validation rejects, and provider rate-limit responses. Use the kill switch for rollback; do not delete accepted queue or Health data.

Rollback sets `SUUNTO_HEALTH_SYNC_ENABLED` to false and deploys the affected Functions. New schedules and webhooks then stop Health work, already queued Health rows are acknowledged as provider-disabled without calling Suunto, and the availability callable makes the History Import UI sleep-only even when an older Health sync-state document remains. Existing imported Health data remains until account deletion; Sleep continues independently.
