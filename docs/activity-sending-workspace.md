# Activity sending workspace

`/send-activities` and `/send-activities/{suunto,coros,wahoo}` are authenticated, noindex workspaces for recorded activities. The page is viewable without Pro; preparing and starting delivery require the backend's real Pro entitlement, including its existing grace policy. Lapsed owners can read results, remove draft files, stop unstarted work, and check accepted operations. Existing automatic sync settings, historical callables and direct-upload endpoints remain compatible. Route/course uploads remain in Connections.

## Review and delivery

Choose one destination and either local FIT/FIT.gz files or saved QS activities. Connections, an owned activity's actions, and the dashboard's selection toolbar link here. Selection never sends automatically. The destination account is pinned privately when the draft is created and checked again before confirmation. Reconnecting a different account requires a new draft.

Local bytes are validated server-side as complete recorded FIT, with bounded gzip expansion and sport/category warnings. They become a private temporary source, without creating an event, archive metadata, or automatic-sync setting. Limits are 50 local files per batch, 20 MiB compressed and expanded per file, and 200 MiB reserved temporary storage per owner. SHA-256 identity and an immutable Storage generation make staging retries idempotent. Failed transfers keep the reservation until removal or expiry; reselecting the same file resumes it. Files removed from a draft require a new draft to be selected again.

Saved selections accept up to 50 explicit event IDs, or sources and inclusive ISO date bounds generated from the user's local calendar days. Date-range scans use bounded 50-event pages and an opaque server-owned cursor. Validated, canonical selection criteria remain private with the operation; after a reload, Continue saved-activity preview resumes them and the current cursor without depending on browser selection state. The display exposes only a Boolean that the selection was retained. Each original must pass the existing owner/provenance/generation eligibility boundary, plus this workspace's size and recording checks. Excluded originals, including deleted explicit selections, receive an explanatory row. Empty ranges finish review with no eligible activities and cannot be confirmed. Merged/derived events and unsupported or missing originals do not become queue work. The workspace neither exports synthesized event data nor rewrites retained originals.

Temporary Storage/read failures during recording review pause the preview with a safe `unavailable` error rather than permanently excluding a recording. Private criteria, the page cursor and successfully reviewed rows stay intact. Continuing retries the failed original without downloading prior reviewed rows or creating provider work. Missing objects and known size, generation or recording validation failures still produce exclusions.

The prepared revision must be explicitly confirmed. The private operation write admits bounded pages through retry-enabled Firestore triggers, reusing `activitySyncQueue` and its existing task dispatcher, leases, rate limits, fingerprints and provider workers. Local sources use `deliveryMode: direct`; saved sources use `historical`. No new queue or provider credentials are introduced. Queue linkage is private and commits atomically with admission before task dispatch, so Stop can always inspect unstarted work. Stale admission pages cannot overwrite a claimed operation. A background projection rereads current queue state and publishes a strict allowlist of display fields. Duplicate trigger delivery cannot inflate finished counts. Duplicate local sources that schedule no new work immediately release their extra storage reservation.

The finished count includes delivered, duplicate/excluded, stopped and needs-action rows. It is not a success percentage. Transfer progress measures bytes; waiting for provider processing has no invented percentage. Global processing jobs survive page navigation and are reconciled from confirmed operations separately from recent-history reads.

Delivery details combine recorded provider-claim starts with worker retry history. Explicit restart atomically retires the previous claim and any reset legacy retry fallback into server-private source-row `priorAttempts`, alongside the queue reset. Projection adds that retained history to the current claim and worker retry count, so restarting does not erase completed attempts. Rejected duplicate retries and repeated projections cannot inflate it; an unclaimed resume adds no claim. Missing history defaults to zero, with no reconstruction of previously lost attempts. Worker retry budgets, task generations and cumulative worker retry counters keep their existing semantics.

| State/recovery | Behavior |
| --- | --- |
| Preparing / ready | Private staging and review; no provider delivery yet |
| Queued / sending | Durable admission or a claimed provider operation |
| Waiting for provider | Accepted operation; poll its retained upload identifier |
| Delivered / already exists | Provider-confirmed result, distinct from HTTP acknowledgement |
| Connection issue / Pro lapse | Review Connections or restore Pro. Resume sending is permitted only for an unclaimed, unaccepted original within its source window and reviewed account; accepted identifiers stay protected |
| Check status | Resume the existing accepted operation, including after Pro lapse |
| Retry sending | Available only after a typed provider status response confirms processing failed, within the source window, with current Pro |
| Acceptance unknown | Requires checking the provider; no automatic or manual workspace resend |
| Stop unsent | Stop work without an operation claim or accepted identifier; close confirmed-failure retries and release their temporary copies |

A new batch cannot overwrite a claimed/accepted delivery for the same source and destination. Already admitted work retains its pinned account. A status check on an active operation does not dispatch another task; restarting a terminal status check creates a new task generation without changing its upload ID. Explicit restart after confirmed failure is the only workspace command that clears that operation's IDs. Existing automatic delivery's restart policy is unchanged.

The display projection includes the sending deadline and stopped flag. Closed windows hide Send/Retry/Resume while preserving accepted status checks and draft-file removal. An open page refreshes its deadline every minute and rechecks it on sending actions. Copied deep links restore the batch's stored destination and source without sending or haptic feedback. Recent-send and browser-history context changes discard only the previous view's selection invalidation; rejected navigation and the same draft retain it. Selection feedback follows accepted navigation. Loading or unavailable batch reads cannot create replacement drafts; confirmation waits for readable review rows. Row loading has an explicit status and permits only one paging request at a time. History and row errors remain visible until their own recovery. Aborted file transfers settle with recovery instructions rather than leaving the view busy. Source filters apply to explicit activity selections as well as date ranges. Delivery details use the shared Material Show/Hide disclosure.

The activity menu and selection toolbar emit selection feedback only after navigation to the workspace succeeds. Pending or cancelled navigation stays silent. The bulk action's accessible label names review and the selected activity count; opening the workspace never starts provider delivery.

Opening a created draft must succeed before local uploads or saved preview start. A cancelled navigation leaves an empty draft recoverable from Recent sends and reports an error in the current view. Changing destination, source or batch during an action permanently fences its follow-up commands and feedback, including before create replies and when navigation returns to the original values. The action's own accepted draft navigation and unrelated query changes for the same draft remain active. Existing staged rows can be resumed from their draft; confirmed backend work continues independently.

## Persistence and cleanup

- `users/{uid}/activitySends/{id}` and its `rows`: owner-readable display projection, server-write-only, available independently of subscription. These contain no provider IDs, file paths, digests, credentials, continuation URLs, or raw errors.
- `users/{uid}/activitySendOperations/{id}` and `rows`: server-only account pin, cursor, reservations, original provenance, queue references and expiry.
- `users/{uid}/activitySendQuota/current`: server-only transactional byte reservation.
- `users/{uid}/activitySendSources/{batch}/{row}.fit`: private immutable temporary local bytes. Existing Storage rules permit owner reads and deny client writes; public event sharing does not expose this prefix.
- `activitySendUploadCleanup/{pathHash}`: backend-only permanent leaf reservation created atomically with quota/source staging before Storage I/O. It survives recursive user deletion, has no TTL, and permits only the exact derived temporary row path.

Unconfirmed drafts expire after 24 hours. Confirmed local sources are usable for seven days; delivered/stopped sources are removed earlier. Hourly cleanup removes expired objects with exact generation checks, releases reservations idempotently and prevents unclaimed expired work from starting. Accepted uploads retain their provider identifiers and can finish without the source. Display/private batch trees are recursively pruned 30 days from creation. Scheduled cleanup failures can delay physical deletion; the expiry boundary still blocks new temporary-source reads. Retained saved-event originals follow their existing archive retention policy and are never deleted by this feature.

History pruning keeps the private operation's expiry marker until cleanup succeeds. It recursively removes the public display tree, then every private child collection, then the private root. This preserves the next scheduled retry even if Firestore removes a document root while a descendant deletion fails. Nested and missing-parent descendants remain discoverable through the marker; pruning never touches retained archive events or accepted queue identifiers.

Removing a draft row atomically records private `cleanupPending` intent with the display deletion and revision change. The command acknowledges that committed removal; it does not hold its reply for Storage deletion. The existing retry-enabled operation trigger drains pending cleanup in pages of 50, including drafts and expired/stopped sends, and schedules the next page through a private operation progress write. Successful exact-generation deletion and transactional quota release clear the intent together. A failed cleanup remains retryable even though the browser no longer has a row to act on. Saved-original removals clear only the marker and never delete archive objects. Late staging cannot adopt a removed row. Account-deletion guards remain authoritative before background work and inside release/progress transactions.

Staging save, metadata-read and adoption failures share the cleanup path. A failed upload that outlives its removed/retired reservation rearms private cleanup intent and an operation write; active failed uploads keep their reservation for same-file resumption. Cleanup inspects the current generation of a retired local object rather than assuming its original generation still exists. A private cleanup revision prevents an older Storage completion from erasing a newer request. Expiry cleanup also rechecks retired local paths with zero reserved bytes, releasing quota only once.

The external upload reservation protects in-flight writes for 15 minutes, beyond the 120-second upload handler and the Storage SDK's 600-second retry deadline. Same-file retry renews it in the guarded quota/source transaction. Successful adoption also retains the delayed reservation; reconciliation discards it only after a fresh committed-source/account check. Failed active previews defer cleanup to draft expiry and stay resumable. Unknown/rejected writes retain the reservation even after successful inline deletion, because the object can appear later. Adoption rejects a superseding cleanup claim.

The existing hourly cleanup job re-drives at most 500 external reservations in 100-document pages. A transaction rereads the current lease, source and account-deletion guard before claiming cleanup; an active tombstone overrides remaining adopted-source documents. Cleanup claims last 30 minutes, beyond its 300-second handler plus separate metadata-read and delete SDK retry deadlines, and block staging. Reconciliation validates the marker identity, exact temporary path and stored digest before deleting a current exact generation. Failure retains the claim and retries after 30 minutes. Completed cleanup deletes only the same claimed permanent leaf, never a replacement reservation or user state. Saved archive originals are outside this scope. Account-prefix cleanup invokes the same bounded reconciler even when prefix deletion fails; active leases remain for the scheduler to finish. The collection uses default single-field indexes on `cleanupAfter` and `userID`, with no TTL or new composite index.

Sending authority is checked before processing and again inside the provider-claim transaction for both local and saved sources. Reconnection cannot reopen unaccepted work after Stop or expiry; it may continue an existing accepted operation and preserves the workspace queue's original 30-day retention. Explicit retries clear the prior attempt's upload ID, workout key, result code, continuation and prepared type before creating a fresh claim, while retaining the reviewed account pin.

Stop commits its intent before cleanup. The existing retry-enabled operation trigger reconciles all private source rows in 50-row pages, including previously admitted or Pro-lapsed rows. Its private cursor advances only after row transactions and exact-generation cleanup succeed, so interrupted callable replies and cleanup failures resume safely. Active claimed/accepted or uncertain operations retain their source and status path; Stop never resets their provider identifiers. A processed, skipped, provider-confirmed failure retains its result and identifiers but releases its temporary file and quota because Stop closes its retry authority. If processing fails after Stop reconciliation has completed, the retry-enabled delivery projection performs that release on the later terminal result. Storage errors retry the projection without losing identifiers or releasing quota twice. Open batches retain failed sources for explicit retry. The workspace offers Stop for these retryable results even when the finished batch is complete or Pro has lapsed; failure messages describe the result without promising a retry outside its window. Saved archive originals are preserved. Staging and saved-preview transactions reject new rows or late adoption after Stop. A connection failure after a claim without an accepted identifier projects acceptance uncertainty and requires checking the provider directly.

Every mutation transaction checks the existing user root and deletion tombstone. Background writers no-op for deleted/deleting accounts. Account deletion additionally deletes the exact feature Storage prefix; staging finishing after deletion cannot adopt its source. The user-data extension recursively removes the two user-owned Firestore trees. Workspace queue records retain accepted-operation identifiers for 30 days, matching display history; legacy queue records keep their existing TTL. Both use existing account queue cleanup.

## Backend and MCP impact

The callable is an internal versioned command union: create, prepare, confirm, remove, stop, check, retry. The HTTP endpoint accepts authenticated/AppCheck-verified binary FIT staging with a fixed header contract. Backend ownership is required for byte parsing, immutable source/quota reservation, private account/provenance inspection, and admission/status/retry authority. SDK listeners read only display projections; clients cannot write operations or quotas.

MCP impact: no new tools, scopes, consent, metrics, Assistant access, or provider-delivery mutation is exposed. Existing event reads continue to see archived activities only. Training plans and planned-workout provider delivery are unaffected. Future MCP activity sending requires its own focused proposal/confirmation and consent review; possession of existing activity or Training grants does not authorize it.

## Operations and release boundary

The Admin activity queue separates historical sends, manual origins and direct temporary files. The [delivery monitoring bundle](activity-delivery-monitoring.md) includes fixed `direct` mode, explicit confirmed processing failures, bounded dispatcher observation and hourly source-cleanup failures. No identifiers or raw error strings enter its labels. Admission/projection triggers use retry-enabled Firestore delivery; native function error/latency logs remain their diagnosis surface.

Release requires separate approval for Functions, Rules, indexes and Hosting deployment, and applying the monitoring bundle. Configure the collection-group `activitySendOperations.cleanupAfter` index before the cleanup scheduler runs. New exports have direct loader ownership and trigger-contract checks; no new secrets are required. Follow existing deployment safety commands and read back metrics/policies after activation. Implementation tests use demo emulators and synthetic recordings; they do not call fitness providers or mutate production.

## Follow-up product ideas

Consider an account selector and account-scoped delivery history if multiple destination accounts become a supported product workflow. Existing success/queue deduplication remains scoped to the service and original; reconnecting another account does not reset previous delivery history. Add provider deep links only when a confirmed operation returns a trustworthy recording URL. Older-send search/filtering and an explicit completion recap could improve large histories without treating the finished count as a success metric. Broader file-format export should remain an explicit, reviewed conversion workflow rather than silently synthesizing a recording from QS data.
